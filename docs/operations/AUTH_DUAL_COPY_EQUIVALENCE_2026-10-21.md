# Exact comparison of duplicate Auth COPY records (2026-10-21)

The **fifth actual protected restore**, [39648552202](https://github.com/orlandoue/dialektik-cloud-dev/actions/runs/39648552202), conclusively categorized the first duplicate-key as OTHER_AUTH_COPY. The original separately encrypted-and-verified Auth custom archive was already restored (26 TABLE DATA entries, 82 migration versions validated). The general application `data.sql` then attempted a second COPY into the Auth schema. Duplicate content is therefore plausible but **NOT YET PROVEN EQUAL**.

The new gate parses COPY blocks from (1) the general original data.sql, and (2) `pg_restore --data-only --file` from the separately verified, original managed Auth archive. It compares, for EVERY Auth COPY in the general data.sql, the exact table identity, exact ordered column list, and all COPY record text as a MULTISET (including duplicate row multiplicity). It also checks that any simple duplicated Auth `setval` statement is identical to one in the archive. Unknown COPY grammar, duplicates, truncated blocks, differing rows/column orders, unmatched table, differing sequences, empty Auth scope or IO errors fail closed.

Only Auth COPY blocks AND proven-identical Auth sequence statements can be removed from a derived application replay file, leaving all other source SQL byte-for-byte untouched and in order. The separately restored, original Auth archive remains the authority for those rows. This is not a generic `ON CONFLICT DO NOTHING` or a deletion/overwrite. Do not treat this gate as authorization if an Auth row differs between the two independent capture times.

The code prints only fixed success/failure codes; no table identifiers, source rows, paths, or source names appear in workflow output. Only CI fixtures contain fictional synthetic identities. The real-backed protected invocation remains subject to explicit approved replay and will not open backup credentials from this feature branch. No remote DEV changes. Full Restore Gate #4 also requires subsequent application data PASS, FK/RLS/schema validations, Auth login and independent rollback checks.
